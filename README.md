# Cortex FirewallAlertAnalyst

A worked example of an **Agentix agent** for Palo Alto Cortex XSIAM, built to exercise every
content type and every action capability the demisto-sdk supports - and to document the
places where the platform does not behave the way the SDK implies.

If you are building your first Agentix agent, the two files worth reading are:

- **[`Packs/FirewallAlertAnalyst/AGENT_SPEC.md`](Packs/FirewallAlertAnalyst/AGENT_SPEC.md)** -
  a dry spec of what a pack must contain: every field, every AG/GR validator with its limit
  and whether it is mandatory, and the server rules the SDK does not encode.
- **[`Packs/FirewallAlertAnalyst/README.md`](Packs/FirewallAlertAnalyst/README.md)** - what
  each file in the pack demonstrates, and the naming convention it uses.

## The agent

`firewall-alert-analyst-agent` triages one firewall alert end to end: it scores it
deterministically in Python, reads the case for context, pulls only the traffic that answers
a stated question, judges it with an LLM prompt, and drafts an escalation note. It never
proposes containment, but will execute a block when an analyst names an address.

It ships seven actions covering four `underlyingcontentitem` types:

| Action | Type | Notes |
| --- | --- | --- |
| Score Firewall Alert | `script` | Python automation, full arg-flag set |
| Get Case Details | `command` | bound via `_any_` to `core-get-cases` |
| Search Firewall Logs | `command` | async XQL, approval-gated |
| Get Firewall Search Results | `command` | polling discipline in `fewshots` |
| Triage Firewall Alert | `prompt` | `isllm` script on the `Pro` model tier |
| Draft Escalation Note | `script` | the `isgeneratable` split |
| Block IP | `playbook` | wraps `Block IP - Generic v3` |

Plus one skill, one knowledge collection, and an evaluator test per action.

## Using it

Requires [demisto-sdk](https://github.com/demisto/demisto-sdk) and a Cortex XSIAM tenant.

```bash
export DEMISTO_BASE_URL="https://api-<tenant>.xdr.<region>.paloaltonetworks.com"
export DEMISTO_API_KEY="<key>"
export XSIAM_AUTH_ID="<auth id>"

# Validate. The --config-path matters: the SDK's DEFAULT config selects 15 codes and
# NOT ONE agentix rule, so without it the agent, actions and skills go unchecked.
demisto-sdk validate -i Packs/FirewallAlertAnalyst --config-path validation_config.toml

# Upload
demisto-sdk upload -i Packs/FirewallAlertAnalyst -z --marketplace platform
```

To remove it again (asynchronous, ~1 minute):

```
POST /xsoar/contentpacks/installed/delete   {"IDs": ["FirewallAlertAnalyst"]}
```

## What it depends on

Present on most tenants:

- `Cortex Core - Platform` for `core-get-cases`
- an XQL integration for `xdr-xql-generic-query` / `xdr-xql-get-query-results`
- the `Block IP - Generic v3` playbook
- an LLM on the `Pro` tier (change `promptConfig.modelTier` in
  `Scripts/TriageFirewallAlertPrompt/` to `Thinking` or `Flash` to use another)

The firewall search targets the `panw_ngfw_traffic_raw` dataset with `source_ip` /
`dest_ip` / `dest_port`. Point it at your own dataset if you use a different firewall.

### The two MCP actions will not resolve for you

The agent's `actionids` include two entries beginning `mcp_Generic_MCP_Cortex_Docs_MCP_`.
These are **not in this pack and cannot be** - MCP tool actions are generated by the
platform when you configure a `Generic MCP` integration instance, and their type is
rejected by the SDK.

They are included on purpose, because binding to them is the point: a pack agent CAN
reference platform-generated MCP actions by id, which is the only way to put MCP tools on
an agent from content. The ids embed the instance name, so they resolve only on a tenant
carrying a `Generic MCP` instance named exactly `Cortex Docs MCP` pointed at
`https://cortex-docs.paloaltonetworks.com/~gitbook/mcp`.

Everywhere else they are inert - the other seven actions work regardless. Create that
instance to see it work, or delete the two lines from
`AgentixAgents/firewall-alert-analyst-agent/firewall-alert-analyst-agent.yml` and the
matching block in the skill body. See `AGENT_SPEC.md` section 16.

## Known not to work

A pack cannot ship knowledge text. A Collection carries a name and a description and
nothing else, so the collection this pack uploads lands on the tenant empty and the
agent's knowledge lookup returns nothing. That is left visible rather than hidden: the
escalation codes the agent needs live only in that collection, so the agent should tell
you it cannot find them and ask.

Documents belong to a separate object, the knowledge source, which demisto-sdk cannot
author. Knowledge Center is not supported by the SDK yet, confirmed by its developers on
2026-09-28. Creating a source is a single API call, and the same call scopes it to named
agents instead of sharing it with every agent on the tenant. So an agent with real
knowledge ships in two steps, not one. See AGENT_SPEC.md section 11 and the pack README.
